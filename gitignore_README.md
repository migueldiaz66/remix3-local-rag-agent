# .gitignore, explained

`.gitignore` carries a comment above every rule. This file gives each rule the room a one-line
comment does not have, and says what is tracked on purpose. Whoever changes a rule changes its
comment and this file in the same edit (CONTRIBUTING.md).

## Purpose

Tells git which files in this repository are never tracked: what `npm i` and `npm run build:flow`
produce, what the app writes while it runs, and what the operating system leaves behind. The
rule is simple: a file that a command can rebuild, or that is data rather than source, stays out
of the repository.

How a pattern is read: a pattern with a slash inside is anchored to the repository root; one
without a slash matches at any depth below; a trailing slash matches a folder only.

## The rules

- `node_modules/`: the installed packages, at any depth. `npm i` rebuilds them from
  `package.json` and `package-lock.json`. Tens of thousands of files, none of them source.
- `db/*.sqlite`: SQLite database files directly under `db/`, should the app or a script
  ever create one. Local data, never source. The folder itself, if it exists, may be tracked.
- `tmp/`: scratch folders named `tmp` at any depth. Scripts and people drop temporary files
  there; nothing in them is a source.
- `.DS_Store`: the metadata file macOS Finder writes in every folder it opens. Noise, in case
  the project is ever opened on a Mac.
- `app/actions/public/flow/flow-bundle.js`: the React Flow island, bundled by
  `npm run build:flow` (`scripts/build-flow.ts`) from the sources beside it. Rebuilt before every
  `dev`, `hmr` and `start` by the `pre*` scripts, so it must never be committed: it would go
  stale and produce merge conflicts.
- `app/actions/public/flow/flow-bundle.js.map`: the bundle's source map, written with it.
- `app/actions/public/flow/flow-bundle.css`: the bundle's stylesheet, written with it.

The three bundle rules are listed one by one, rather than as `flow-bundle.*`, so that each line
carries its own comment and so that a future `flow-bundle.d.ts`, should one be written by hand,
would not be hidden by accident.

## Tracked on purpose

- `package-lock.json`: makes `npm i` reproducible; CONTRIBUTING.md lists it as machine-written
  and left alone.
- `docs/callers.md`: generated by `npm run callers`, but tracked so the "Called by" lines can be
  checked against it in a review without running anything.
- `.nvmrc`: tracked so everyone uses the same Node.

## Who reads it

- git: `status`, `add`, `commit` and `clean` skip ignored files; `git add -f` can still force
  one in.
- Tools that honour `.gitignore` by default: ripgrep (`rg`) and some editors' search skip the
  ignored files, which is why a search for the bundle finds nothing.
- Not npm, Node, TypeScript or esbuild: they have their own rules (`exclude` in
  `tsconfig.json`, the skip of `flow-bundle*` in `scripts/callers.ts` and
  `scripts/check-comments.ts`).

A subfolder may carry its own `.gitignore`; it adds to this one for the files below it.

## What breaks if it is wrong

- `node_modules/` removed: the next `git add .` stages tens of thousands of files and the
  repository grows by hundreds of megabytes.
- A bundle rule removed: the built file is committed, every `npm run dev` changes it, and two
  branches conflict on a generated file.
- `db/*.sqlite` removed: local data is committed, possibly with content from the corpus.
- A rule too broad (for instance `*.css` instead of the bundle's path): the hand-written
  stylesheets stop being tracked and are lost on a fresh clone.
- A pattern misspelt: nothing warns; the file simply shows up in `git status`.
